For a long time, my default response to a UI problem was simple.

“Add more state.”

Something didn’t update? Add state.
Something looked wrong? Add state.
Something felt fragile? Add state.

That pattern works for a while. Then it starts to feel like the code is fighting itself.

This post is not about a single React trick. It is about the state audit that helped me stop adding state as a reflex, and start asking better questions.

## When state becomes a liability

State is useful when it stores information that truly changes over time.
But not every value in your component belongs there.

These are the warning signs that your component has too much state:

- You have more than one state variable representing the same idea.
- You find yourself syncing updates across multiple hooks.
- A small UI change requires touching two or three separate state setters.
- You introduce `useEffect` just to keep state values in sync.
- The component works, but it feels fragile and hard to reason about.

If this sounds familiar, you are not alone.

## The state audit: three questions before adding state

Before you reach for `useState`, ask yourself:

1. **Can this value be derived from existing props or state?**
2. **Does this value represent a real event or piece of data, or just a UI condition?**
3. **Will storing it make the component harder to keep in sync?**

If the answer is “yes” to the first question and “probably” to the third, do not add state yet.

## The better pattern: derive instead of store

Here is the refactor that changed everything.

### Before: duplicate state

```jsx
const [selectedItem, setSelectedItem] = useState(null)
const [isItemSelected, setIsItemSelected] = useState(false)
const [activeIndex, setActiveIndex] = useState(null)
```

The component was trying to keep three values aligned.
That means three opportunities for them to drift apart.

### After: one source of truth

```jsx
const [selectedItem, setSelectedItem] = useState(null)

const isItemSelected = selectedItem !== null
const activeIndex = items.findIndex(item => item.id === selectedItem?.id)
```

Now the state is simple.
The rendered UI comes from derived values.
This is the same idea as “computed properties” in other frameworks.

## What to derive instead of store

These values usually belong outside of state:

- checkbox checked state
- selected / active flags
- disabled / hidden conditions
- index values computed from data
- counts or summary values

If the value can be calculated during render and it does not need to be preserved between renders, it usually should not be state.

## When state is still the right choice

There are cases where state is the correct answer:

- form input values that must persist while editing
- whether a modal is open or closed
- user preferences saved in local UI
- network loading status
- any value that represents a discrete interaction over time

The key is that the value must represent a real, discrete fact about the component, not just a display condition.

## Refactoring strategy for a simpler component

1. Identify the state variables that are derived from other values.
2. Replace them with `const` declarations.
3. Keep the minimal state that represents the actual user intent.
4. Remove any effects that only exist to sync derived values.

### Example: simplify the click handler

Before:

```jsx
onClick={() => {
  setSelectedItem(item)
  setIsItemSelected(true)
  setActiveIndex(index)
}}
```

After:

```jsx
onClick={() => {
  setSelectedItem(item)
}}
```

The component behavior remains the same. The state is now easier to reason about.

## A practical checklist for cleaner React state

- Can this value be derived from existing state or props?
- Will this value ever need to update independently?
- Is the value part of the data model, or just a view condition?
- Do I need a hook to keep it in sync?
- If I remove this state, does the component become clearer?

If you can answer “yes” to the last question, you likely should.

## Why this matters

Too much state is not just a performance problem.
It is a maintainability problem.

When state is duplicated, your component can still work.
It just becomes harder to change without introducing subtle bugs.

The best React components are not the ones with the fewest lines of code.
They are the ones where the data and the UI agree.

## The lesson

State is a tool, not a habit.
Use it when you need it.
Stop using it when it starts to fight your own component.

If you want a simple rule of thumb:

> Store the minimal amount of state needed to represent the actual intent of the UI.

The rest can be derived.

Once you start asking better questions, your code becomes calmer, faster, and easier to change.

To this:

```jsx
onClick={() => setSelectedItem(item)}
```

That alone felt like a win.

## This Was Not Really About React

This wasn’t a React trick.

It was a thinking shift.

I had been treating state as “any value that changes over time.”

That definition is incomplete.

A better question is:

Does this value need to be remembered, or can it be calculated?

If it can be calculated from props, existing state, or current data, it probably doesn’t belong in state.

## Why Extra State Is Risky

Extra state is not just extra code.

It creates relationships.

When two states represent the same idea in different forms, you introduce a syncing problem.

And syncing problems are subtle.

They don’t fail loudly.  
They fail quietly.  
Only after certain clicks.  
Only in certain sequences.

Those are the hardest bugs to debug.

## I Started Seeing This Pattern Everywhere

After this experience, I noticed how often I added unnecessary state.

Examples:

- Storing `filteredItems` instead of filtering during render  
- Storing `isFormValid` instead of deriving it from inputs  
- Storing `buttonDisabled` instead of checking conditions inline  

Each time, removing state made the component easier to read and easier to change.

Not faster.  
Not cleverer.  
Just clearer.

## When State Is the Right Choice

This is not an anti-state argument.

Some things should be state:

- User input  
- UI toggles  
- Network responses  
- Temporary UI memory  

The difference is intent.

State should represent user intent or external change.

Not convenience.  
Not duplication.  
Not fear of re-renders.

## A Simple Check I Use Now

Before adding state, I ask myself:

1. Can I derive this from existing state or props?  
2. If this gets out of sync, would it cause bugs?  
3. Does the user actually change this value?  

If the answer to the first is yes and the second is also yes, it probably shouldn’t be state.

## The Unexpected Benefit

The biggest change wasn’t technical.

It was confidence.

I trusted my components more.

When bugs appeared, there were fewer places to look.  
When requirements changed, fewer things broke.

That confidence didn’t come from writing more code.

It came from deleting it.

## Final Thought

Removing state doesn’t feel productive at first.

There’s no new feature.  
No visible improvement.  
No exciting commit message.

But over time, it adds up.

Your components get quieter.  
Your logic gets sharper.  
Your bugs get rarer.

Sometimes the best fix isn’t adding one more hook.

It’s realizing you never needed it.
