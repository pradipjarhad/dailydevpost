I didn’t start by choosing a tech stack for my developer blog.

I started by noticing something uncomfortable (which eventually led me to [learning in public](/blog/why-i-decided-to-learn-in-public-now)).

I was avoiding my own blog.

Not because I had nothing to say.  
Not because the ideas were unclear.  
But because opening the project felt heavier than writing the post.

That friction matters more than people admit.

When writing feels like work before the work begins, you stop doing it. Quietly. Without drama.

This post is not about the “best” stack.  
It’s about the one that finally stopped getting in my way.

## What I needed from the stack

My goal was not to build a product site.
It was to build a developer blog with:

- long-form posts that include code
- predictable routing and layout
- easy metadata management
- content that lives in a code repository
- minimal ceremony for publishing

Those constraints shaped every choice.

## The stack criteria I used

Instead of asking “What is trendy?”, I asked:

- Will this keep the writing flow smooth?
- Will this make it easy to refactor later?
- Can I understand the full system without hunting through too many tools?
- Does this feel like a codebase, not a CMS?

If the stack added noise, I rejected it.

## Why I chose Next.js

Yes, Next.js is more than a blog needs.

That is the point.

I chose it because it removed decisions.

- routing became file-based
- layouts became obvious
- metadata stayed next to the page
- the app felt like a code repository

With many static site generators, you learn the tool.
With Next.js, you write the project.

That made the blog feel more natural.

## Why the App Router mattered

At first, I didn’t care about the App Router.
I thought it was just a new pattern.

It changed the way the project felt.

Layouts stopped being clever. They became boring in a good way.

Pages became files again, not abstractions.

SEO logic lived next to the page.

This matters when you return after weeks away.

## Why I used Tailwind for a writing-first site

I’ve written CSS for years.

Tailwind helped me make styling predictable.

- no cascade surprises
- fixed typography decisions
- consistent spacing

The real benefit was mental quiet.

When the prose looked right, I did not have to think about CSS anymore.

## Why I chose MDX

Plain markdown is simple, but it becomes limiting quickly.

Code blocks are not just decoration.
They are part of the argument.

MDX lets content behave like code.

It lets me use callouts, reusable components, and side notes without hacking around the format.

Yes, it adds complexity.
But it removes more friction than it creates.

## Why Contentlayer matters

Raw MDX works until it doesn't.

Once you have many posts, structure becomes important.

Contentlayer gives you:

- typed content data
- predictable frontmatter
- build-time errors that point to the problem

That made refactoring posts feel safer.

It also made the repo feel more like a content codebase.

## Why Netlify instead of Vercel

I wanted hosting that disappeared.

Netlify felt boring in the right way.

- predictable builds
- clear deploys
- no surprises

For a content-heavy blog, that is a feature.

I did not want hosting to compete with writing.

## The real trade-offs in this setup

This stack is not perfect.

- build times can grow as content grows
- MDX errors can be annoying
- App Router patterns can be confusing at first

The real cost is accepting a little complexity for more control.

If you want zero setup, this is not the stack for you.

## Who should use this stack

This stack fits you if you want:

- a writing-first blog in a code repo
- easy internal linking and SEO
- a content workflow that feels like code
- a system you can maintain yourself

It is not the right choice if you want:

- a visual editor
- rare publishing
- a lightweight, no-code blog
- to avoid reading build logs

## How to choose your own blog stack

If you are picking a stack, use this decision checklist:

- What is the main thing I want to build?
- Will this stack keep the authoring flow smooth?
- Will I be able to understand the whole system after a week away?
- Does this stack feel like a codebase or like a CMS?
- What will I have to learn just to publish one post?

The best stack is the one that helps you ship content reliably.

## What I want other developers to know

The stack is not the story.

The story is the work you get done.

If the technology helps you write and refactor without friction, then it is the right stack.

If it gets in the way, it is not.

That is the decision I made for this blog.

## What Actually Mattered in the End

The signal wasn’t performance.  
Or SEO scores.  
Or Lighthouse numbers.

The signal was silence.

Weeks passed without me thinking about the stack.  
Posts accumulated without friction.  
I stopped questioning tools.

I wrote more because the system stopped asking for attention.

That’s the real test.

Not how impressive the setup looks.  
But whether it lets you come back easily.

This one did.

That’s why I kept it.
