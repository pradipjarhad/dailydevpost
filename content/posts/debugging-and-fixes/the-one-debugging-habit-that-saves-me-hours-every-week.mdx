If you asked me a few years ago what debugging was, I would have said something like this:

"Fixing bugs by trying things until the app works."

That sounds honest, but it also explains why debugging used to drain my energy.

I would stare at the screen.
Refresh the page again and again.
Add a `console.log` here.
Delete it.
Add another one there.
Comment out half the file.
Uncomment it.
Reload.
Hope.

Sometimes it worked.
Often it didn't.
And even when it did, I wasn't sure *why*.

Then one habit changed everything.

Not a tool.
Not a framework.
Not a debugger feature.

A habit.

Today, this one habit saves me more time than anything else I do while debugging.

## The habit: write down what you believe is happening

Before I touch the code, I write down what I think the program is doing.

Not in my head.
Not vaguely.
Not emotionally.

I write it in plain language.
Step by step.

That is it.

It sounds almost too simple.
But it changes everything.

## Why this works

When a bug appears, your brain starts guessing.

Maybe this state is wrong.
Maybe the API is slow.
Maybe the hook is broken.

Guessing is dangerous.

It leads to random changes.
Random changes lead to accidental fixes.
Accidental fixes lead to fragile code.

Writing forces you to be honest.
It changes "maybe" into testable beliefs.

## The three things I write down

### 1. What I expect to happen

Keep it behavioral.

> When I click the Save button, the form data should be sent and I should see a success message.

No framework jargon.
No implementation details.

### 2. What is actually happening

Be literal.

> When I click the Save button, nothing happens. No request is sent. No error is shown.

Or:

> The request is sent, but the UI does not update.

This separates facts from feelings.

### 3. What I believe the code is doing

This is the key part.

> I believe the click handler runs.
> I believe it calls the submit function.
> I believe the submit function exits early because `isValid` is false.
> I believe `isValid` is false because the state has not updated.

That is where debugging becomes scientific.

## A real debugging session using this habit

Here is how this played out in a real project.

I had a React component that felt slow. The UI was not broken. Nothing crashed. Filters worked. Data appeared. But interactions felt sticky in a way I couldn't name.

**Step 1: I wrote down what I expected.**

> Filtering the list should feel instant. The UI should respond within one render cycle of the filter change.

**Step 2: I wrote down what was actually happening.**

> Every time I change the filter, there is a brief but noticeable lag. The list flickers. Unrelated parts of the page also seem to flash.

**Step 3: I wrote down my beliefs.**

> I believe the filter is causing the parent to re-render.
> I believe that parent re-render causes the list component to also re-render.
> I believe the list component is doing expensive work on every render.
> I believe the expensive work is the filtering itself, running inline without memoization.

**Step 4: I tested each belief.**

I opened React DevTools and enabled "Highlight updates." Belief 2 was confirmed immediately: the list was flashing on every filter change, along with things that had nothing to do with the filter.

I checked where objects were created. One line created a new options object inside render and passed it as a prop. That object was the cause. It had a new reference on every render, which told the list component that its props had changed, which triggered a full re-render of every item.

```jsx
// Before: new reference every render
<ItemList
  options={{ sortOrder: 'asc', showEmpty: false }}
  onItemClick={(item) => handleItemClick(item)}
/>
```

```jsx
// After: stable references
const listOptions = useMemo(
  () => ({ sortOrder: 'asc', showEmpty: false }),
  []
)

const handleClick = useCallback(
  (item) => handleItemClick(item),
  [handleItemClick]
)

<ItemList
  options={listOptions}
  onItemClick={handleClick}
/>
```

One line.
One fix.
Problem solved.

Without the belief-writing habit, I would have spent an hour guessing. With it, I had a clear hypothesis within five minutes and a fix within ten.

## Turning debugging into yes/no questions

Write a belief.
Test it.
Confirm or reject.

For example:

> I believe the click handler runs.

Add a `console.log` at the top of the handler.

- If you see the log: belief confirmed.
- If you do not: belief rejected.

Then move to the next belief.

This is not glamorous.
It is effective.

## A practical template

When a bug appears, write:

1. **Expected behavior**
2. **Actual behavior**
3. **Beliefs**

Then test each belief.

Example:

> Expected: The save button submits the form.
> Actual: The button does nothing.
> Belief 1: The click handler executes.
> Belief 2: The handler calls submit.
> Belief 3: Submit does not exit early.

Now debug by checking each item.

## Why this habit saves time

At first, it feels slower.
You want to get straight to the code.

But the truth is this:
Most debugging time is spent fixing the wrong problem.

This habit prevents that.

You verify beliefs one by one.
You do not guess.

The few minutes spent writing beliefs consistently saves thirty to sixty minutes of random code changes, refreshes, and frustrated searching.

## This habit makes debugging calmer

Debugging used to stress me out.
Now it feels quieter.

When you write down what you believe, the problem stops feeling huge.

It becomes smaller.
Contained.
Understandable.

Instead of battling the bug, you understand it.

That mental shift matters. Clear thinking produces better fixes.

## Why it works when you are tired

Late nights. Deadlines. Low energy.

This habit still works.

You do not need to be clever.
You only need to verify beliefs.

That is a stable process. It does not require inspiration or expertise. It requires honesty.

## How it improves your code long-term

When you write down what you believe the code does, your code becomes clearer.

You:

- name things better
- separate responsibilities naturally
- avoid hidden side effects

If you cannot explain what a function does in one sentence, that is a signal.
The habit teaches you to notice that signal before it becomes a bug.

## This habit scales with experience

Beginners benefit from this habit because it gives them structure when everything feels overwhelming.

Senior developers benefit from it because it removes the "hero" impulse: the urge to make a big, clever change before understanding the problem fully.

The difference is only in complexity.
Same habit.
Different depth.

## Final thought

Debugging did not get easier because I learned more APIs.

It got easier because I stopped lying to myself about what I knew.

Writing down your beliefs forces honesty.
Honesty is the fastest path to fixing bugs.

**Don't fight the bug.**
**Understand it.**
