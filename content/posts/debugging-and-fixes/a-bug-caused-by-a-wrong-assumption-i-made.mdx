This bug did not come from a complex algorithm.
It did not come from a race condition.
It did not come from an exotic edge case.

It came from a wrong assumption.

And the worst part is the assumption felt reasonable.
It felt obvious.
It felt safe.

That’s why it stuck.

## When “working” is not the same as “correct"

The application looked fine.
The UI rendered.
The network requests completed.
No red errors.

This is the exact moment when assumptions become dangerous.
If you never question what you believe about your data, you will keep building the same fragile structure.

## The assumption that broke the feature

This time, my assumption was:

> “This data will only change when the user explicitly triggers an action.”

That assumption showed up in three places:

- initial state from props
- effect hooks with empty dependency arrays
- memoized values that never recomputed

Those are the most common places assumptions hide in React code.

## How I found the bug

The bug was subtle.
It did not crash the app. It only showed up after some time.
So I treated the investigation like a detective case.

### Step 1: write down what you believe

Before changing code, I wrote:

- I believe the data is immutable until a user event.
- I believe `props.items` never changes.
- I believe the effect only needs to run once.

This is the most important step.
If you cannot clearly state your assumption, you cannot debug it.

### Step 2: confirm or reject each belief

I added minimal instrumentation:

```js
useEffect(() => {
  console.log('fetchData run')
  fetchData()
}, [])
```

```js
console.log('items changed', items)
```

Then I reproduced the scenario.
The logs showed the data changing even when I had not clicked anything.

That rejected the most dangerous assumption: the data was not static.

### Step 3: inspect the code that depends on that assumption

I found two problems:

1. `useState(props.items)` was only initialized once.
2. a memoized value used `[]` as its dependency list.

That combination meant the component kept stale data intentionally.

## The fix: trust the data flow, not the assumption

The safest rule I adopted was:

> If a value can change from props, do not initialize it in state without an update mechanism.

In practice, this means:

- avoid `useState(props.something)` unless you manage updates explicitly
- prefer derived values when the source is props
- keep effect dependencies honest

### Before

```js
const [items, setItems] = useState(props.items)

useEffect(() => {
  fetchData()
}, [])

const processedItems = useMemo(() => {
  return items.filter(item => item.active)
}, [])
```

### After

```js
const items = props.items

useEffect(() => {
  fetchData()
}, [fetchData])

const processedItems = useMemo(() => {
  return items.filter(item => item.active)
}, [items])
```

Now the component recomputed when the data changed.
The bug disappeared.

## A better debugging checklist for assumptions

When you feel confident in your code, run through these questions:

- Did I assume a prop never changes?
- Did I only initialize state once from props?
- Did I use `[]` in a dependency list because the code “should only run once”?
- Am I memoizing something that really depends on changing values?
- If the data changes outside my component, can this component respond?

If the answer is yes to any of those, you likely have an assumption waiting to break.

## Why this matters beyond React

This bug was not special to React.
It was special to any code that treats the world as stable when it is not.

The real skill is not writing the code that works today.
It is writing the code that still works when reality changes.

That is what makes a fix durable.
That is what makes engineering reliable.

## The lesson

When your app is “working,” the next important question is:

> What have I assumed without testing?

Answer that question honestly.
Then write the code so it does not depend on the answer.

> Props change → state updates automatically

But React never promised that.

That belief came from my own [mental shortcut](/blog/one-mental-model-that-made-react-easier-for-me).

## Why This Bug Was Dangerous

This bug wasn’t loud.

It didn’t:

- Throw errors  
- Break builds  
- Fail tests

It quietly made the UI drift out of sync with reality.

Those are the worst bugs.

Users don’t report them clearly.  
They just lose trust.

They think:

- “Sometimes it works”  
- “Sometimes it doesn’t”

And eventually, they stop using the product.

## The Real Root Cause

The bug wasn’t:

- React  
- Hooks  
- The API  
- The backend

The real cause was this:

> **I designed the code around how I expected the system to behave, not how it actually behaved.**

I optimized for a scenario that existed only in my head.

## Fixing the Bug

The fix was not complex.

I:

- Removed derived state where it wasn’t needed  
- Let props stay as props  
- Added real dependencies to effects (and stopped making [this mistake with useEffect](/blog/one-mistake-i-made-with-useeffect-and-how-i-think-about-it-now))  
- Allowed re-renders to happen naturally

```js
const items = props.items

useEffect(() => {
  process(items)
}, [items])
```

The code became slightly longer.  
Slightly less “clean”.

But much more honest.

And that mattered more.

## What I Learned From This

### 1. Assumptions Are Invisible Bugs

They don’t show up in code reviews easily.

They show up as thoughts like:

- “This will never change”  
- “We don’t need to handle that”  
- “It’s safe to ignore this case”

That’s where bugs grow.

### 2. Working Code Can Still Be Wrong

If the UI looks fine today, it doesn’t mean it will look fine tomorrow.

Especially when:

- Data changes over time  
- Multiple parts affect the same state  
- The app grows

Silence is not proof of correctness.

### 3. Simplicity Can Be Misleading

Simple code is good.  
But oversimplified assumptions are not.

Complexity doesn’t disappear just because you ignore it.

It waits.

### 4. React Does Exactly What You Tell It To

React didn’t betray me.

It followed my instructions perfectly.

I told it:

- Initialize once  
- Don’t re-run  
- Trust this value

It trusted me.

That trust was misplaced.

## How I Think About Code Now

Now, I ask different questions.

Not:

> “Does this work right now?”

But:

- “What am I assuming here?”  
- “What breaks if this changes?”  
- “What am I telling React to ignore?”

I care less about:

- Fewer lines  
- Clever tricks  
- Early optimization

And more about:

- Clear behavior  
- Honest dependencies  
- Predictable updates

## A Small Mental Shift

One idea helped me a lot:

> **Treat assumptions as bugs that haven’t happened yet.**

If your code relies on something never changing, write that down.

If it feels “obvious”, question it.

Because software rarely stays the way we imagine it.

## Final Thought

This bug didn’t make me feel smart.

It made me feel humbled.

The mistake wasn’t technical.  
It was human.

I assumed.  
I trusted that assumption.  
And I built on top of it.

Now, I still make assumptions.

But I try to notice them.

Because most bugs don’t come from what we don’t know.

They come from what we’re too sure about.
