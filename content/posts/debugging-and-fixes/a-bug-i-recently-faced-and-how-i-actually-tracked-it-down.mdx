This bug did not crash the app.

Nothing turned red.
No stack trace appeared.

The UI loaded.
Buttons worked.
Data appeared on the screen.

That is why it took longer than it should have to notice something was wrong.

## When slow is the bug

The first clue was not an error.
It was a feeling.

The interface felt heavy.
Clicking a filter felt sticky.
Typing in the search input caused visible delay.

That feeling matters.

A page can work and still be broken.
Slow interactions are a real failure mode, not a "nice to have" fix.

The mistake I almost made was dismissing it. "It works, it's probably fine." But this particular list was used by support staff every day. That stickiness added real friction to their workflow.

## My first wrong assumption

My first instinct was the API.

I opened the Network tab.
Requests were fast, under 100ms.
Responses were small, a few hundred items, no large payloads.

The list was not enormous. Around 300 items.

So I blamed the browser. Then I blamed the device. Then I blamed React in general.

None of that was it.

The moment I stopped guessing and started observing, the real problem appeared within two minutes.

## Stop guessing, start observing

I opened React DevTools.

The specific step: **Settings → General → Highlight updates when components render.**

I then interacted with the filter dropdown.

Every time I changed the filter:

- the entire list flashed
- unrelated sidebar components flashed
- even the search input wrapper flashed

That meant the page was re-rendering components that had nothing to do with the filter change.

## What React DevTools was actually showing

React flashes a component when it re-renders. A slow, deliberate flash usually means a render took time. A fast, constant flash means it is re-rendering for small or no reason.

The Profiler tab confirmed this. I recorded one filter interaction:

- `FilterDropdown` rendered (expected)
- `ItemList` rendered (expected, the data changed)
- `ItemCard` rendered **for all 300 items** (not expected, only the filtered result changed)
- `PageSidebar` rendered (completely unexpected)

The total render cost for one filter interaction was around 40ms. Not catastrophic on my machine. But on the support team's older laptops, it was 200ms or more. That is the sticky feeling.

## The real problem was identity, not logic

React does not re-render because your code looks different.
It re-renders because the props it receives are **different by reference**.

In this case, two issues stood out when I read the component carefully.

**Issue 1:** An inline callback recreated `onItemClick` on every render.

```jsx
// This creates a new function every time the parent renders
<ItemList
  items={filteredItems}
  onItemClick={(item) => handleItemClick(item)}
/>
```

Every parent render → new function reference → `ItemList` receives a "new" prop → `ItemList` re-renders → all 300 `ItemCard` children re-render.

**Issue 2:** The filtering logic was inline, creating a new array on every render.

```jsx
// This creates a new array every render
const filteredItems = items.filter(item => {
  return item.category === selectedCategory
})
```

Even when `selectedCategory` had not changed, a parent re-render (from something unrelated, like the sidebar toggle) would create a fresh `filteredItems` array. New array reference → `ItemList` sees new props → full re-render.

Combined, these two patterns turned the list into a re-render machine.

## What I tried first (and why it didn't help)

My first attempt was wrapping `ItemList` in `React.memo`.

```jsx
const ItemList = React.memo(function ItemList({ items, onItemClick }) {
  return items.map(item => (
    <ItemCard key={item.id} data={item} onClick={() => onItemClick(item)} />
  ))
})
```

This helped slightly, but not enough. Why?

Because `React.memo` does a shallow comparison of props. The inline callback `(item) => handleItemClick(item)` was still recreated on every render, giving `ItemList` a new `onItemClick` reference each time. `React.memo` saw the change and re-rendered anyway.

The fix had to go one level deeper.

## Fix 1: stabilize the callback

```jsx
// Before
<ItemList
  items={filteredItems}
  onItemClick={(item) => handleItemClick(item)}
/>

// After
const handleClick = useCallback(
  (item) => handleItemClick(item),
  [handleItemClick]
)

<ItemList
  items={filteredItems}
  onItemClick={handleClick}
/>
```

`useCallback` returns the same function reference as long as `handleItemClick` doesn't change. Now `ItemList` receives a stable `onItemClick` prop and `React.memo` can do its job.

## Fix 2: memoize the derived array

```jsx
// Before
const filteredItems = items.filter(item => {
  return item.category === selectedCategory
})

// After
const filteredItems = useMemo(
  () => items.filter(item => item.category === selectedCategory),
  [items, selectedCategory]
)
```

Now `filteredItems` only produces a new array reference when `items` or `selectedCategory` actually changes. Unrelated parent re-renders no longer cause the list to re-render.

## Fix 3: check child props too

Even with the above fixes, `ItemCard` was still creating a new inline function:

```jsx
// Inside ItemList: before
{items.map(item => (
  <ItemCard
    key={item.id}
    data={item}
    onClick={() => onItemClick(item)}  // new function every render
  />
))}
```

This meant every `ItemCard` re-rendered when `ItemList` rendered, even if the item data had not changed.

The fix:

```jsx
// After: pass the stable callback, let ItemCard handle the binding
{items.map(item => (
  <ItemCard
    key={item.id}
    data={item}
    onClick={onItemClick}  // stable reference from useCallback
    itemId={item.id}       // let ItemCard construct the argument
  />
))}
```

And inside `ItemCard`:

```jsx
const ItemCard = React.memo(function ItemCard({ data, onClick, itemId }) {
  const handleClick = useCallback(
    () => onClick({ id: itemId, ...data }),
    [onClick, itemId, data]
  )

  return <div onClick={handleClick}>{data.name}</div>
})
```

Now `ItemCard` only re-renders when its own data changes.

## The result

After these three changes:

- One filter interaction dropped from 40ms to 4ms on my machine
- On the support team's older laptops, the improvement was even more dramatic
- The sidebar no longer flashed during filter changes
- The search input felt immediate

The list became what it should have been from the start: just a list.

## A step-by-step investigation process

Looking back, here is the process that worked:

1. **Trust the feeling** because slow UI is a signal, not a distraction.
2. **Observe before changing.** Use React DevTools Highlight Updates before touching any code.
3. **Use the Profiler.** Record one interaction and look at what rendered, not just that it rendered.
4. **Identify unstable props:** callbacks, arrays, objects created inline.
5. **Change one thing at a time.** Fix the callback first, measure, then fix the derived data.
6. **Measure again.** Verify the improvement is real, not assumed.

## Why this bug is so common

It is easy to mistake React's re-renders for wrong behavior.

There was nothing wrong with the data.
There was nothing wrong with the logic.

The bug was that the app was doing far more rendering work than necessary, because small reference identity choices had compounded across the component tree.

## What I changed after this

I now treat these patterns like early warnings when I see them in new code:

- inline functions passed as props to list components
- derived values (filtered, sorted, mapped arrays) created inline without `useMemo`
- empty dependency arrays used for convenience rather than accuracy

Not because I want to optimize prematurely.
But because these patterns often hide real work that compounds silently.

## The real lesson

If an app feels slow and still works, the problem is often in the render path.

Before reaching for complex solutions, ask:

> Are the props I pass stable between renders?

If not, fix that first.

It will make the app feel faster, and make the code much easier to reason about.
