Three hours.

That is how long I spent debugging a component last week that I had built from scratch two weeks earlier.

Not a large component. Not a complex feature. A user profile card with some editing logic. Maybe 80 lines of JSX when I first wrote it.

By the time I needed to change it, it had grown to 200 lines, had three pieces of state that were more or less syncing the same idea, had two effects that I could not fully explain, and had a prop interface that no longer matched what the component actually did.

I built that mess. And I built it exactly the way I always build components: by starting with the JSX.

That is the habit I am changing this week.

## How I usually build components (and why it causes problems)

My default process looks like this:

1. Open a new file
2. Start writing JSX: what does this need to render?
3. Notice I need some state: add `useState`
4. Notice I need to fetch something: add `useEffect`
5. Notice a prop is missing: add it to the interface
6. Fix things until it works
7. Ship it and move on

This feels productive because things are appearing on screen quickly. The component takes shape fast.

The problem is that I am making all my architectural decisions in the middle of the implementation. And architectural decisions made in the middle of an implementation are the most expensive kind to undo.

When I add that third `useState` because the logic feels easier that way, I am making a structural choice with incomplete information. When I add an `useEffect` to "sync" two pieces of state, I am usually working around a design problem I did not notice yet. When I add a prop "just in case," I am speculating about the future and adding surface area to the interface without a reason.

All of these decisions accumulate. Three weeks later, when a requirement changes slightly, every one of them becomes a constraint that makes the change harder.

## The component I should have written

Here is a simplified version of what the profile card actually became:

```jsx
function UserProfileCard({ userId }) {
  const [userData, setUserData] = useState(null)
  const [isEditing, setIsEditing] = useState(false)
  const [editedName, setEditedName] = useState('')
  const [isSaving, setIsSaving] = useState(false)
  const [error, setError] = useState(null)

  useEffect(() => {
    fetchUser(userId).then(data => {
      setUserData(data)
      setEditedName(data.name) // sync the edit state
    })
  }, [userId])

  const handleSave = async () => {
    setIsSaving(true)
    try {
      await updateUser(userId, { name: editedName })
      setUserData(prev => ({ ...prev, name: editedName })) // sync again
      setIsEditing(false)
    } catch (e) {
      setError(e.message)
    } finally {
      setIsSaving(false)
    }
  }

  // ... 80 more lines
}
```

See the problem? `editedName` is synced from `userData.name` in the effect, and then `userData` is synced back from `editedName` on save. Two pieces of state representing the same concept. An effect that exists only to sync them. A save handler that needs to update both.

Every time I changed one, I had to remember to update the other.

## What I should have started with

If I had stopped before writing any code and answered one question, "What is this component responsible for?", I would have written something like this:

> `UserProfileCard` displays a user's profile. It does not own the user data. It receives `user` and `onSave` as props. It manages a local editing state that is discarded on cancel and submitted via `onSave` on confirm.

That description reveals something immediately: this component does not need to fetch data at all. Fetching is the parent's job. The card just displays and edits.

With that clarity, the implementation becomes:

```jsx
function UserProfileCard({ user, onSave, isSaving }) {
  const [editedName, setEditedName] = useState(user.name)
  const [isEditing, setIsEditing] = useState(false)

  const handleCancel = () => {
    setEditedName(user.name) // reset to what we received
    setIsEditing(false)
  }

  const handleSave = () => {
    onSave({ name: editedName })
    setIsEditing(false)
  }

  if (!isEditing) {
    return (
      <div>
        <span>{user.name}</span>
        <button onClick={() => setIsEditing(true)}>Edit</button>
      </div>
    )
  }

  return (
    <div>
      <input
        value={editedName}
        onChange={e => setEditedName(e.target.value)}
      />
      <button onClick={handleSave} disabled={isSaving}>
        {isSaving ? 'Saving...' : 'Save'}
      </button>
      <button onClick={handleCancel}>Cancel</button>
    </div>
  )
}
```

No effects. No syncing. No ambiguity about who owns the data. The component does exactly one thing: let the user view and optionally edit a name, and report the result upward.

The parent now owns fetching and saving:

```jsx
function ProfilePage({ userId }) {
  const { user, refetch } = useUser(userId)
  const [isSaving, setIsSaving] = useState(false)

  const handleSave = async (updates) => {
    setIsSaving(true)
    await updateUser(userId, updates)
    await refetch()
    setIsSaving(false)
  }

  return (
    <UserProfileCard
      user={user}
      onSave={handleSave}
      isSaving={isSaving}
    />
  )
}
```

This separation is cleaner, easier to test, and easier to change. If the save logic needs to change, I change the parent. If the display logic needs to change, I change the card.

## The template I am starting with this week

Before I write any JSX, I am going to answer these four questions in a comment at the top of the file:

```jsx
// Responsibility: displays user profile data and handles inline editing
// Does NOT: fetch data, manage save requests, know about userId
// Props: user (object), onSave (function), isSaving (boolean)
// States: isEditing (local), editedName (local draft, discarded on cancel)
```

That is 4 lines. It takes maybe 30 seconds.

But those 30 seconds force me to decide the component's boundaries before I have any implementation to defend. Once you start writing JSX, you develop attachment to the approach. The mental cost of changing direction goes up. Planning before you start keeps the cost low.

## What this does to the codebase over time

The individual effect is small. One component with clear responsibility is not dramatically different from one component with fuzzy responsibility, at least not immediately.

The compounding effect is the difference.

A codebase where most components have clear, defended boundaries is a codebase where:

- changes are localized, so you know what you are allowed to touch
- bugs are easier to find because the component is not doing six things that could be wrong
- reviews are faster since the reviewer can see immediately whether the component stays within its declared scope
- new engineers onboard faster because the component's purpose is readable without running the code

I have worked in codebases on both ends of this spectrum. The difference in daily friction is not subtle.

## The habit I am actually building

The habit is not "write a description first." The habit is "decide the component's job before you implement it."

The description is just a forcing function for the decision.

If I can write a clean two-sentence description of what a component does and does not do, the implementation usually follows naturally. If I cannot write that description, it means I do not understand the design well enough yet. And implementing something I do not understand yet is how I get back to three hours of debugging.

The description is the signal. The implementation is the output.

## Final thought

The biggest React improvements I have made rarely came from learning a new API.

They came from changing one small habit.

This one is small. It costs 30 seconds per component. It has already saved me hours.

The most valuable assumption to challenge is this:

> "I can start writing before I understand the component clearly."

If you can not answer "what does this component do and not do?" in one sentence, wait until you can.

The code will be better for it.
